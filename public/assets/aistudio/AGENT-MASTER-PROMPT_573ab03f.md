# MASTER PROMPT --- Tarbwy Event Manager WordPress Plugin

أنت فريق هندسي خبير في WordPress وPHP وMySQL وأمن التطبيقات والاختبارات.
مهمتك بناء إضافة WordPress كاملة قابلة للتثبيت والإنتاج باسم **Tarbwy
Event Manager**. اقرأ `TARBWY-EVENT-MANAGER-SPEC.md` كاملاً واعتبره
المرجع الوظيفي والتقني الأساسي.

## المعطيات الثابتة

-   الموقع: `tarbwy.org`
-   صفحة الحدث: `/launch`
-   VIP RSVP: `/launch/vip`
-   Check-in: `/launch/checkin`
-   Ticket: مسار آمن ضمن `/launch/ticket`
-   العربية فقط، RTL.
-   500 شخص إجمالاً بمن فيهم المرافقون.
-   لكل مرافق سجل مستقل وQR مستقل.
-   استضافة WordPress الحالية، MySQL/MariaDB، واتصال Online يوم الحدث.
-   لا تخترع تاريخاً أو مكاناً أو أسماء متحدثين أو هوية بصرية. اجعلها
    إعدادات قابلة للتحرير.

## قواعد إلزامية

1.  ابدأ بفحص المشروع والبيئة وإصدارات PHP وWordPress وMySQL والقالب
    والإضافات وحدود الاستضافة. لا تفترض أن بيئة العمل فارغة.
2.  اعرض خطة التنفيذ، هيكل الملفات، الجداول، المخاطر والتعارضات قبل
    البرمجة.
3.  لا تعدل WordPress Core أو القالب أو ملفات إضافات أخرى.
4.  لا تضع أسرار SMTP أو مفاتيح API أو بيانات دخول في المصدر أو Git.
5.  لا تستخدم React/Vue/Next/Laravel أو خدمة SaaS منفصلة أو CDN وقت
    التشغيل. المطلوب Plugin PHP تعمل داخل WordPress مع JavaScript وCSS
    محليين.
6.  لا تستخدم خدمة QR خارجية ولا ترسل إليها بيانات الضيوف.
7.  لا تترك TODO أو أزراراً شكلية في وظائف أساسية.
8.  لا تدّعِ تنفيذ أو اختبار شيء لم تنفذه فعلياً.
9.  إذا ظهر قرار يؤثر في الأمن أو البيانات أو سياسة القبول ولم تحسمه
    المواصفات، وثّقه في `DECISIONS.md` واطلب التوضيح قبل التخمين.
10. طوّر على Staging أولاً، ولا تنشر إلى الإنتاج قبل النسخ الاحتياطي
    والاختبار.

## مراحل التنفيذ

### A --- Discovery

-   افحص بنية المشروع والبيئة والتوافق.
-   حدّد ما إذا كان Elementor أو Gutenberg مستخدماً دون تغيير القالب.
-   اعرض خطة ومخاطر ومتطلبات الاستضافة.
-   إذا لم تتوفر بيئة WordPress فعلية، جهّز فحص توافق وبيئة اختبار محلية
    موثقة، ولا تزعم أنك فحصت الإنتاج.

### B --- Plugin Foundation

-   أنشئ إضافة منظمة بفئات ومسؤوليات منفصلة وnamespace فريد مثل
    `Tarbwy\\EventManager`.
-   أنشئ activation/deactivation hooks، installer، schema version
    ومigrations.
-   استخدم `$wpdb->prefix` الفعلي وInnoDB.
-   لا تحذف بيانات الحدث عند تعطيل الإضافة.
-   أضف فحص متطلبات ورسائل خطأ إدارية واضحة.
-   اتبع WordPress Coding Standards وtext domain ثابت.

### C --- Database & Domain

نفّذ الجداول الواردة في المواصفات: events, registrations, guests,
invitations, tickets, checkins, email_logs, activity_log. - افصل
`review_status` و`rsvp_status` و`checkin_status`. - استخدم فهارس وقيود
uniqueness. - لا تجعل البريد فريداً عالمياً؛ قد يتشارك المرافقون بريداً
واحداً. - استخدم prepared statements لكل SQL ديناميكي. - اجعل منطق
الأعمال منفصلاً عن العرض.

### D --- Admin Dashboard

أنشئ لوحة عربية RTL تشمل Dashboard وGuest List وRegistration Requests
وVIP Invitations وTickets وCheck-in وReports وSettings وEmail Logs. أنشئ
capabilities دقيقة: `manage_tarbwy_events`,
`review_tarbwy_registrations`, `manage_tarbwy_guests`,
`manage_tarbwy_invitations`, `checkin_tarbwy_guests`,
`export_tarbwy_reports`. أنشئ أدوار Event Administrator وRegistration
Manager وCheck-in Staff. موظف الاستقبال لا يملك صلاحية إدارة الطلبات أو
التصدير أو إعدادات الموقع. استخدم pagination وفلاتر وبحثاً فعلياً.

### E --- Public Registration

-   أنشئ `/launch` متوافقاً مع WordPress ولا يفرض قالباً على الموقع كله.
-   اسمح بدمج Landing Page مع Gutenberg/Elementor عبر shortcode أو block
    خفيف عند الحاجة.
-   اجعل حقول النموذج قابلة للتعديل لأن الاستمارة الرسمية ستصل لاحقاً.
-   أنشئ registration group وسجلاً مستقلاً للضيف وكل مرافق.
-   يبدأ الطلب `pending`، وتظهر رسالة أن الطلب قيد المراجعة وليس تأكيد
    حضور.
-   أرسل رسالة استلام وإشعار فريق الحدث.
-   نفّذ server-side validation وhoneypot/rate limit وحماية من التكرار.
-   لا تصدر QR للـpending أو waitlist أو declined.
-   عند قبول طلب الجمهور، اتبع `approval_auto_confirms`، والافتراضي
    true: القبول يفعّل التأكيد ويصدر QR للأشخاص الذين اعتمدهم المدير. يجب
    السماح باعتماد بعض المرافقين واستبعاد آخرين.

### F --- VIP RSVP

-   استيراد CSV مع preview وdry-run وتقرير أخطاء.
-   لا ترسل الدعوات تلقائياً بعد الاستيراد إلا بعد تأكيد المدير.
-   أنشئ token قوي باستخدام `random_bytes()` وخزّن SHA-256 hash فقط.
-   لا تستخدم ID أو البريد كرمز.
-   لا تعرض بيانات المدعو قبل التحقق من الرمز.
-   اسمح بالإبطال وإعادة الإصدار والانتهاء.
-   RSVP: «سأحضر» أو «أعتذر». الحضور يحوّل الحالة إلى `confirmed` مباشرة،
    والاعتذار إلى `declined`.
-   المرافقون أفراد مستقلون بحد يحدده المدير.
-   أرسل رسائل مناسبة وسجل كل تغيير.

### G --- QR & Tickets

-   QR منفصل لكل شخص مؤكد، بمن فيهم المرافقون.
-   لا تضع PII أو guest ID في QR.
-   استخدم token عشوائياً قوياً، وخزّن hash فقط.
-   لا تصدر تذكرة لغير المؤهل.
-   ألغِ التذكرة القديمة قبل إعادة الإصدار.
-   أنشئ بطاقة HTML printable آمنة؛ PDF اختياري إذا كانت المكتبة مستقرة.
-   لا تستخدم ID متسلسلاً كرابط تذكرة.

### H --- Check-in

-   واجهة `/launch/checkin` عربية RTL ومناسبة للهاتف والتابلت.
-   استخدم مكتبة JavaScript محلية موثوقة لقراءة QR بالكاميرا.
-   وفر بحثاً بالاسم/البريد/رقم التذكرة وManual Check-in.
-   اعرض valid/already checked-in/revoked/unknown/not confirmed بوضوح.
-   كل الأجهزة تتصل بالخادم نفسه عبر REST API.
-   لا تعرض نجاحاً قبل تأكيد الخادم.
-   لا تعتمد على localStorage لمنع التكرار.

**شرط حرج:** استخدم UNIQUE constraint على `ticket_id` في جدول checkins،
وعملية ذرية/transaction. لا تستخدم SELECT ثم INSERT غير محمي. اختبر
جهازين يمسحان البطاقة نفسها في الوقت نفسه؛ يجب أن ينجح واحد فقط والآخر
يتلقى Already Checked-in.

### I --- Email

-   استخدم `wp_mail()` عبر طبقة WordPress، قابلة للعمل مع SMTP
    plugin/provider يحدده العميل. لا تفترض أن Brevo متصل.
-   أنشئ قوالب عربية RTL قابلة للتحرير ورسائل الاستلام والقبول والانتظار
    والرفض ودعوات VIP وRSVP والتذكرة والتذكير والشكر.
-   أنشئ queue وسجل محاولات وretries محدودة مع backoff ومنع التكرار.
-   استخدم server cron موثقاً.
-   استخدم timezone الحدث.
-   لا تدّعِ أن قبول `wp_mail()` يثبت وصول البريد إلى Inbox.

### J --- Reports

-   تقارير الطلبات والحالات والضيوف وVIP والمرافقين والمؤكدين والحاضرين
    وNo-shows.
-   CSV UTF-8 BOM لفتح العربية في Excel.
-   حماية CSV formula injection.
-   صلاحية تصدير مستقلة وسجل للتصدير.
-   احسب No-show بعد انتهاء الحدث من المؤكدين ناقص الحاضرين، لكل شخص على
    حدة.

### K --- Security & QA

-   استخدم sanitize عند الإدخال وescape عند الإخراج.
-   كل REST route يجب أن يحتوي `permission_callback`؛ لا تستخدم
    `__return_true` للمسارات الحساسة.
-   استخدم nonces وcapabilities، وتحقق من علاقة كل سجل بالحدث.
-   امنع XSS/SQLi/CSRF/IDOR، وrate limit للنماذج العامة.
-   لا تسجل tokens أو أسراراً أو بيانات حساسة.
-   اكتب اختبارات آلية إن أمكن، واختبارات يدوية موثقة إن لم تتوفر بيئة
    PHPUnit.
-   نفّذ PHP lint لكل الملفات.
-   اختبر كل حالات التسجيل وVIP والQR والتكرار المتزامن والصلاحيات
    والبريد والتصدير.
-   اختبر 500 شخص على الأقل، والهاتف والتابلت، وعدم كسر القالب الحالي.
-   اختبر النسخ الاحتياطي والاستعادة على Staging.

## متطلبات جودة التنفيذ

-   PHP متوافق مع البيئة الفعلية، لا تفترض إصداراً قبل الفحص.
-   استخدم WordPress APIs عند الإمكان.
-   لا تستخدم eval أو remote code loading أو shell commands.
-   لا تعرض SQL أو stack traces للمستخدم.
-   استخدم pagination ولا تحمل كامل قاعدة الضيوف في الواجهة.
-   polling للإحصائيات خفيف (10--20 ثانية عند الحاجة).
-   اجعل المحتوى والتاريخ والمكان والشعار والألوان إعدادات؛ لا تخترع
    بيانات.
-   اجعل 500 هو إجمالي العدد بما فيه المرافقون.
-   لا تضف ميزات خارج النطاق إلا لضرورة موثقة.

## التسليم النهائي

أنشئ: - مجلد `tarbwy-event-manager/`. - `tarbwy-event-manager.zip` قابل
للتثبيت. - `README-AR.md` للتثبيت والإعداد. - `ADMIN-GUIDE-AR.md` لفريق
تربوي. - `TECHNICAL-GUIDE.md`. - `TEST-REPORT.md` بنتائج الاختبارات
الفعلية. - `CHANGELOG.md`. - `DECISIONS.md`. - `UNINSTALL.md` لسياسة
الاحتفاظ/حذف البيانات.

متطلبات الاستضافة، وما ينتظر تربوي: الشعار والهوية والنصوص والاستمارة
وقائمة VIP وSMTP وسياسة الخصوصية. أعطِ خطوات التثبيت على Staging ثم
الإنتاج. لا تضع أسراراً في التقرير.
